# M23.10 — Presentation polish: dev overlay, post-processing, board boot, game-event panels, HUD chrome

Status: **in progress 2026-10-31: §1 implemented; §2–§7 not started.** Builds on M23.9
(`docs/plan/M23.9-manifold-emission-and-handoff.md`): LED emission, per-cell panel
channels, `PanelResponse`, the per-emitter living transition, `view::handoffState`, the
backdrop and star pass, and `BoardOptions::presentationIntensity`.

Goal: move the game screen from a strong prototype to a festival-ready demo. Fix what
reads as unfinished (developer text, flat dark image, a loose HUD), and add two signature
moments, board boot and game-end power-down, that reuse the LED/hologram machinery.

Out of scope, by the user's decision:
- Camera framing. The camera is free.
- Piece mesh fixes. The dark rings will be fixed when a human remodels the pieces.
- Sound. The user will do it.
- Key art and trailer content. The user will do them.
- The wireframe ambient field in menus. It stays there; only the game screen changes
  (see §6).

Slices, in order. Each slice is implemented test first, verified with captures, and kept
green.

| Slice | What |
|---|---|
| §1 | Dev overlay toggle (and the debug-access docs it relies on) |
| §2 | Post-processing: HDR scene, emissive bloom, tone map, grain/dither |
| §3 | Board boot sequence |
| §4 | Check ripple |
| §5 | Game-end power-down (and power-up on undo) |
| §6 | Game-screen ambient: stars only |
| §7 | HUD chrome that uses the space around the stage |

General rules for every slice:
- **Pure in explicit time.** Every animation is a function of explicit seconds or
  progress (visual time, event age), so `--shot`/`--clip` with `--t`, `--visual-time` or
  the new event-time flags reproduce bit-for-bit.
- **Intensity.** Every new animated effect is scaled by
  `BoardOptions::presentationIntensity`. At 0 it degrades to the calm form described in
  its section, never to "nothing happens" where an event needs to be communicated.
- **Debug access** (AGENTS.md rule 9). Every feature gets a console command or a setting,
  plus a CLI flag where headless capture needs one. Update `DebugConsole::help()`,
  `docs/debug-console.md` and the AGENTS.md command examples.
- **Vertex inputs stay at 16 or fewer.** M23.9 packed the board pipeline to exactly 16. New
  per-cell event state must not add vertex attributes. Use a per-frame storage buffer
  indexed by a per-instance cell index (see §3.3), or pack into existing channels.
- **Gameplay cues win.** Selection, legal-move, last-move, check, seams and portals must
  stay at least as distinguishable as today in every frame of every effect, except where
  a section explicitly says a cue is dimmed (the power-down hold).
- **Theme gating.** LED-specific effects (§3–§5 panel parts) apply where the cells use LED
  material. Other themes get the calm or fallback form stated per section.

## §1 Dev overlay toggle

### Behaviour

A single boolean, **dev overlay**, which is off by default. When it is off, the game
shows no developer-only presentation:

| Element | Location | Off (default) | On |
|---|---|---|---|
| fps counter | `Ui` overlay `##fps`, `src/render/ui.cpp` ~2185 | hidden | shown as today |
| "NOT BUILT" main-menu entries (CONTINUE, MULTIPLAYER) | `src/render/ui_widgets.cpp` ~745, menu list in `ui_menus.cpp` | entries **removed** from the list (the remaining entries renumber 01..N) | shown as today, disabled, with "NOT BUILT" |
| Debug hint strings, if any are added later | — | hidden | shown |

- The variant plate's geometry line ("flat board", "glued board").

  settings, so `get devOverlay` and `set devOverlay true` already work.

  state.
- A CLI flag `--dev` forces it on for that run, for captures of the dev overlay.

## §2 Post-processing

### Why

The scene is drawn straight into the 8-bit swapchain or capture target
(`OffscreenTarget::kColorFormat`, UNORM). Values clip at 1. Emission has no headroom and
nothing can glow. Dark gradients (backdrop glow, floor spill) band visibly, and stream
compression makes the banding worse. A restrained post stack fixes both without changing
the palette.

### Pipeline

Current order in `BoardRenderer::record` (`src/render/board_renderer.cpp`):

1. The scene pass: backdrop, board, scaffold, shadows, flourish. It has an MSAA resolve
   into `target.colorImage()`.
2. The optional pause blur ping-pong.
3. The overlay (UI) pass.

New order, used when post is enabled:

1. **Scene pass into an HDR image.** Use an `R16G16B16A16_SFLOAT` colour image owned by
   the renderer per frame-in-flight and sized to the target. The MSAA attachment (when on)
   is the same float format and resolves into it. The depth image is unchanged.
2. **Bloom.** Run a bright-pass prefilter into mip 1, at half resolution, with a soft
   threshold:
   - knee: threshold `T = 0.85`, knee width `0.25`, applied to luminance;
   - weights: Karis average on the first downsample to stop fireflies.
   
   Then run downsamples to `N = clamp(floor(log2(min(w,h))) - 3, 3, 6)` levels with a
   13-tap filter, and upsample back with a 3×3 tent, additively. This is the standard
   "dual filter" chain. Bloom textures are float and half resolution down.
3. **Composite into `target.colorImage()`** (the UNORM image). This is a fullscreen pass:
   - `hdr + bloomStrength * bloom`;
   - exposure (fixed 1.0 for now);
   - the tone map (below);
   - vignette, moved here from `backdrop.frag` so it is applied once. Remove the
     backdrop's own vignette term in the same change. Strength stays as today's backdrop
     value;
   - grain plus dither (below).
4. **The pause blur** then runs on the composited image exactly as today.
5. **The overlay (UI) pass** draws on top. The UI is never tone-mapped, bloomed or
   grained.

When post is **disabled**, the order is exactly today's. The old path stays as the
reference and the fallback.

### Tone map: the existing look must survive

The themes were authored for LDR, so the tone map is **identity in the authored range** and
only shoulders highlights.
- `x ≤ K` (with `K = 0.80`) gives `y = x`.
- `x > K` gives `y = K + (1 - K) * (1 - exp(-(x - K) / (1 - K)))`.
- Apply it per channel on max-channel ratio, so hue is preserved: compute it on
  `m = max(r,g,b)`, then scale `rgb *= tm(m) / m`. Clamp to 1.
- Write it as a pure function `render::toneMap(float)` (C++ mirror in a new
  `src/render/post_params.{hpp,cpp}`) with the identical GLSL in the composite shader.

Shader consequence: `board.frag` may now write values above 1 for genuinely emissive
light:
- LED emitter centres (the M23.9 emission term);
- hologram rim and scan emission;
- heat and footprint glow;
- capture and check pulses (§4, §5).

Diffuse and base colours stay at or below 1. Audit each emission term and give it an
explicit HDR gain constant. For example, `kEmitterHdrGain` makes the brightest
light-square emitter land around 1.6–2.0 in HDR, so only emitters bloom, not whole
squares. With post disabled, the same shader output clamps as today.

### Grain and dither

- **Dither:** add triangular-PDF noise of ±1 LSB (±1/255) before quantisation, always on
  when post is on. This removes banding.
- **Grain:** luminance-only noise, amplitude `0.012 * presentationIntensity`, weighted
  toward midtones (`4·y·(1−y)`), at 1:1 pixel scale. It is animated with visual time at
  24 Hz steps (`floor(visualTime * 24)` re-seeds), so it is pure in time.
- Use an integer hash of `(pixel.xy, frameSeed)`. Do not use a noise texture unless a
  blue-noise texture already exists.

### Theme parameters

Add to `view::Theme`:
- `bloomStrength`: manifold `0.06` as a starting point; console/wood `0.0`;
- `grainAmount`: manifold `1.0`; wood `0.6`.

Tone map, dither and vignette apply to every theme when post is on. With
`bloomStrength == 0`, the bloom passes are **skipped**, not run at zero.

### Access

- `Settings::postProcess` (bool, default `true`) and `Settings::bloomScale` (float,
  default `1.0`, multiplies the theme's `bloomStrength`).
- A console alias `post [on|off]`, and `set bloomScale 0.5` through the existing
  `get`/`set`.
- CLI flags `--post 0|1` and `--bloom <scale>`, so before/after A/B captures are one flag.

### Performance

At 1920×1080 on an integrated GPU, the post stack costs at most 1.0 ms. Measure it with
`--bench-frame`, before and after, and record the result in this plan's status. Allocate
images only on resize or format change, never per frame.

### Tests

- Unit (`[render]`):
  - `toneMap` is exactly identity for `x ∈ [0, K]` (bit-equal);
  - it is monotone, continuous at `K`, and below 1 for all finite x;
  - `toneMap(1.0)` is above 0.85;
  - the bloom level count formula holds for 640×360, 1280×720, 1920×1080 and 3840×2160.
- GPU (`tests/render`, lavapipe):
  - (a) A scene with no HDR values (the wood theme, `bloomScale 0`) gives post-on output
    within ±2/255 of post-off output per channel, everywhere outside the vignette change.
    Compare against a post-off render with the same vignette moved; the simplest way is to
    assert the backdrop-vignette removal and the composite vignette produce the same
    pixels within ±2/255.
  - (b) The manifold standard board with bloom on: the mean luminance of a ring of pixels
    just outside a lit light square is higher than with `bloomScale 0`. Pieces and HUD
    pixels change by at most ±3/255 except within N px of emitters.
  - (c) The UI is not affected: a HUD text pixel is identical with post on and off.
  - (d) The validation layers stay clean (the existing `--shot` nonzero-exit contract).
- Captures for review: standard, torus `--geometry` and klein, manifold, with `--post 0`
  and `--post 1`, at 1920×1080. Assemble a contact sheet.

## §3 Board boot sequence

### When it plays

- On entering the Game screen with a **new** session: New Game (after its overture, if
  one plays, starting on the overture's last frame), `load` from the console or CLI, and
  Continue once that is built.
- On **Reset**.
- At the start of each game in Watch mode.
- Not on undo, not on returning from pause or settings, not between trailer beats (the
  trailer has its own transitions), and not in the editor.

### Timeline

Times are seconds since boot start (`bootAge`). Total `kBootSeconds = 1.8`.

| Phase | Time | What |
|---|---|---|
| Bezel | 0.00–0.25 | The plinth/bezel emissive line draws on, travelling from one corner around the perimeter (on the shape view: fades in uniformly). The backdrop glow and floor spill ramp from 0 to their normal level over 0.0–0.6. |
| Panels | 0.10–0.95 | Each cell powers on at `cellOnTime = 0.10 + 0.70 * d(cell)`, where `d ∈ [0,1]` is normalised **rank order from the near edge**. For non-box geometry and the shape view, use normalised graph distance from the first rank's cells (BFS, below). On power-on a cell goes from dark (0.08 of its colour) to an overshoot of 1.35× for 60 ms, two short flickers (dips to 0.5 over 40 ms each, seeded timing), then the **per-emitter living transition** into its colour (M23.9), so every cell sparkles into place. Interference and faults are suppressed until a cell has been on for 0.3 s. |
| Projection | 0.55–1.55 | Pieces appear in a sweep, rank by rank in the same `d` order: `pieceStart = 0.55 + 0.75 * d(cell)`. Each piece's footprint heats up first (0.15 s ramp to full heat, M23.9 heat channel). Then the hologram **reveals bottom to top**: a reveal height `h(t)` rises from 0 to 1 over 0.30 s, and fragments above `h` are discarded. A bright scan band at `h` (the existing scan line, 2× brightness) leads the reveal. Then heat eases back to the standing footprint. |
| Settle | 1.55–1.80 | All effects at their normal levels. The boot ends. |

At intensity 0 (calm), the sequence is a simple 0.4 s fade in: cells and pieces fade
together, with no flicker, overshoot or sweep.

### Input

The board accepts clicks during boot. The first click, keypress or engine move
**completes the boot instantly**: it jumps to `bootAge = kBootSeconds` and the click is
also processed normally. The engine does not start thinking until the boot ends or is
skipped.

### State and data flow

- Add a pure model in `src/view/board_boot.{hpp,cpp}`:
  - `BootState bootState(float bootAge, float d, float intensity)` returns per-cell power
    (0..1+overshoot), flicker multiplier, transition age for the living transition, piece
    reveal height, heat, and bezel progress;
  - plus `float bootCellOrder(...)`, which computes `d` for every cell (below).
- Session owns `bootStartVisualTime` (`std::optional<double>`). It is set at the trigger
  points above and cleared when complete. `Session::bootAge(visualTime)` returns age or
  `nullopt`.
- `d` (boot order): for a box board,
  `rank / (ranks - 1)` on the board's second axis. For higher-dimensional boxes, use the
  lexicographic layer then rank. For glued or other geometry, use BFS over king-step
  adjacency (the geometry's own neighbour function, so wraps count as adjacency) from all
  cells of rank 0, normalised by the maximum distance. Compute it once per session or
  variant and cache it on Session.
- Shader inputs: per-cell `power`, `flicker`, `revealHeight` and the boot heat go in a
  **per-frame storage buffer** `CellFx[cellCount]`, read in `board.vert`/`board.frag`
  through a per-instance cell index. If there is no existing per-instance cell index, pack
  it into an existing integer-safe float channel; do not add an attribute. §4 and §5 reuse
  this buffer, so design it once:

  ```
  struct CellFx {            // std430, 32 bytes
    float power;             // multiplies cell emission; 1 = normal
    float flicker;           // multiplier, 1 = none
    float revealHeight;      // piece reveal 0..1, >=1 = fully shown
    float heat;              // extra footprint heat (adds to M23.9 heat)
    float rippleAmp;         // §4
    float ripplePhase;       // §4
    float tintMix;           // §4/§5 tint toward fxTint
    float glitch;            // §5 forced glitch 0..1
  };
  ```

  Push or uniform: `fxTint` (vec3), `bezelProgress`, `backdropRamp`.
- Backdrop: multiply glow and spill by `backdropRamp`.

### Access

- A console command `boot`, which replays the boot sequence now.
- A CLI flag `--boot-t <s>`, which renders as if `bootAge = s`, for captures. Example:
  `--shot b.ppm --theme manifold --boot-t 0.7`.

### Tests

- `board_boot` unit tests:
  - monotone power-on order by `d`;
  - every cell at power 1 and every piece fully revealed at `bootAge ≥ kBootSeconds`, at
    any intensity;
  - calm intensity has no overshoot or flicker;
  - `bootCellOrder` on standard (rank order), torus (BFS through wrap; values in [0,1])
    and a 3-D box.
- Session tests: trigger points set boot (new session, reset, watch start); undo and
  resume do not. A click during boot completes it and still selects or moves.
- GPU test: at `--boot-t 0.0` the board cells are near-dark; at 0.5 the near ranks are on
  and the far ranks dark; at 2.0 the frame matches the no-boot frame within ±2/255.
- Capture sheet: `--boot-t` 0.1, 0.3, 0.5, 0.8, 1.1, 1.4 and 1.8 on the standard and torus
  boards.

## §4 Check ripple

### Behaviour

When a move gives check (the check cell changes from none, or from one royal to another),
a single interference ripple runs outward from the checked king's cell across the panels:
- **Propagation:** by **board adjacency**, not screen distance. Use BFS over king-step
  neighbours via the geometry, so on a torus the ripple wraps through the seams and visibly
  shows the topology. Speed is `kRippleCellsPerSecond = 14`. The ripple dies out after
  `kRippleSeconds = 0.9` or when it reaches the maximum distance, whichever is first.
- **Look per cell** as the wavefront passes (a Gaussian in time around
  `arrival = dist / speed`, σ = 0.06 s, amplitude falling as `1 / (1 + 0.35·dist)`):
  - a brightness dip then a recovery of at most ±25 % of emission;
  - a one-row emitter shift (the M23.9 glitch row-shift look, but driven, not random);
  - a tint toward the check colour, `tintMix` at most 0.35 at the king's cell and falling
    with distance.
- The king's cell keeps its existing check cue throughout, and the ripple never hides it.
- It fires once per check event, never repeating while the check persists.
- **Calm:** no ripple. The existing check cue alone communicates the check.
- **Non-LED themes:** no ripple.

### Data

- Session records a `checkEvent { CellId king; double visualTimeStart; }` when the check
  cell changes to a valid cell after a move (including engine moves and replays). Undo does
  not fire it.
- A pure function `view::checkRipple(dist, age, intensity)` returns `{amp, phase, tint}`.
  Per-cell BFS distances come from a shared `view::cellDistances(geometry, from)` helper.
  §5 uses the same helper.
- Values are written to `CellFx.rippleAmp`, `ripplePhase` and `tintMix`, with
  `fxTint = theme check colour`.

### Access

- A console command `ripple [<cell>]`, which fires a ripple from the given cell (default:
  the side-to-move's royal cell) without changing game state.
- A CLI flag `--check-t <s>` renders the ripple at age `s` for the current check (use it
  with `--script` that gives check).

### Tests

- `cellDistances` on standard (Chebyshev distance), torus (the wrap shortens distance; a1
  to h1 is 1) and Klein (the twist is respected).
- `checkRipple`: zero before arrival and after `kRippleSeconds`; peak near arrival; zero at
  calm.
- Session: a check-giving move fires the event once; a following non-check move does not;
  undo does not.
- GPU: at `--check-t` equal to the arrival time of a distance-2 cell, that cell differs
  from the no-ripple frame and a distance-6 cell does not.
- Capture sheet on standard and torus.

## §5 Game-end power-down (and power-up on undo)

### Behaviour

When `Game::result()` becomes decided (checkmate, stalemate, draw by any rule, or no legal
moves):

**Decisive (one side wins):**
- **Power-down wave.** It starts at the losing royal's cell (or, with no royal, the losing
  side's last-moved piece's cell) and spreads by board adjacency (the §4 BFS) at 9
  cells/s. As the front passes a cell:
  - a forced glitch burst (`glitch` 1 → 0 over 0.25 s: tear and channel offset, the M23.9
    glitch looks);
  - then power falls to the **hold level 0.30**, never black: the final position must stay
    readable for review;
  - interference and faults continue at that level, sparse, so the board looks damaged
    but alive.
- **Losing side's holograms destabilise.** Over 1.0 s, each losing piece's scan becomes
  irregular: the scan band jitters, there is 1–2 short dropouts (opacity to 0.3 for
  50–80 ms), and it settles at opacity 0.65 with a slow 0.3 Hz shimmer.
- **Winning side's holograms** stay solid and get +15 % emission.
- Game cues in the hold:
  - last-move stays visible;
  - the check cue on the mated king stays visible and is exempt from the dimming (power
    1.0 on that cell), so the final picture reads "this king is mated";
  - legal-move cues are absent anyway.

**Draw:**
- The whole board dims uniformly to **0.55** over 0.8 s, with one soft unison flicker. No
  glitches. Both armies settle at opacity 0.85.

**Calm:** a 0.6 s fade to the hold levels. No glitch, jitter or dropouts.

**Undo (or Reset) out of a finished game:**
- Undo gives a quick **power-up**, 0.5 s: power returns from the hold level with one
  overshoot to 1.15 and then the living transition, and the holograms restabilise.
- Reset uses the full §3 boot instead.

Watch mode: the power-down plays at a watched game's end. The next game then boots (§3).

### Data

- Session records `endEvent { kind: Decisive|Draw; Color loser; CellId origin; double
  visualTimeStart; }` when the result changes from undecided to decided. Undo after a
  decided result records `powerUpEvent { double visualTimeStart; }` and clears
  `endEvent`.
- A pure `view::powerDown(kind, dist, age, intensity)` returns per-cell
  `{power, glitch}`. A pure `view::hologramEnd(side, age, seed, intensity)` returns
  per-piece `{opacity, scanJitter, emissionGain}`.
- Per-piece values reach the hologram shader through existing per-instance channels if
  free. Otherwise add a per-piece entry to the `CellFx` buffer (indexed by the piece's
  cell). Still no new vertex attributes.

### Access

- A console command `endfx win|draw|off [<side>]`, which previews the effect without
  changing the game. `off` clears it.
- A CLI flag `--end-t <s>` renders at end-event age `s` (use it with `--script` that
  reaches mate, or with `setfen` plus a mating move).

### Tests

- `powerDown`:
  - power is 1 before the front arrives;
  - it holds at exactly 0.30 (decisive) or 0.55 (draw) after `age ≥ settle`, for every
    distance;
  - the glitch is nonzero only near arrival;
  - calm has no glitch;
  - power never goes below the hold.
- `hologramEnd`: the loser settles at 0.65 and the winner at 1.0 opacity with gain 1.15;
  draw is 0.85 for both.
- Session:
  - Fool's mate (1. f3 e5 2. g4 Qh4#) fires `endEvent` with Decisive, loser White, and
    origin White's king cell e1;
  - stalemate and draw fire Draw;
  - undo fires the power-up and clears the end event;
  - reset clears both and boots.
- GPU: at `--end-t 3` on a mated position, the mated king's cell is at full brightness and
  a far cell is dimmed to about 30 % ± 5 %.
- Capture sheets: Fool's mate at `--end-t` 0, 0.3, 0.7, 1.2 and 3; a stalemate at the same
  ages.

## §6 Game-screen ambient: stars only

On the game screen, when the M23.9 star pass is drawn (LED-material themes), do **not**
draw the wireframe ambient field (`boardField_.draw(...)` in `Ui::buildGameHud`,
`src/render/ui.cpp` ~1690). Menus, overtures and the trailer keep it. Themes without the
star pass keep the field on the game screen, so they are not left with an empty
background.

  the renderer's star gating and the UI.
- Test: the manifold game screen submits no draw commands to `boardFieldList_`; the
  wood/console game screen still does.

## §7 HUD chrome that uses the space around the stage

### Intent

Today the game HUD is loose text in the corners plus a ribbon of buttons along the bottom.
Replace it with a coherent **instrument frame** around the central stage: the same device
language as the board (dark glass, thin emissive edges, LED-like readouts), using the
edges and corners of the screen rather than a bottom ribbon only. The board stays the
brightest thing on screen. The chrome is quieter than the board and louder than the
background.

This is a design slice. It must **look good** in captures before it merges. If a layout
does not, keep iterating on captures, or fall back to restyling the existing layout with
the panel language below. Do not ship something worse than today.

### Layout (16:9; it adapts to other aspects)

```
┌─[ VARIANT PLATE ]───────────────────────────────[ TURN / STATUS ]─┐
│ STANDARD                                          ● WHITE TO MOVE  │
│ flat board · file→ rank↑                          ply 0 · 20 legal │
│ ▮ file edges meet  ▮ rank edges meet                               │
```

### Panel language (theme tokens only)

  outer corners of each panel.

  colour, the smallest size.
- Readouts (ply, counts, move SAN): the HUD's monospace or tabular-number font, the
  normal size, near-white.
- Three type sizes only: name, readout, label. Map them to the existing font sizes, scaled
  by ui scale.
- An optional, very faint horizontal scanline texture inside panels (1 px every 3 px,
  alpha 0.04), scaled by intensity.
