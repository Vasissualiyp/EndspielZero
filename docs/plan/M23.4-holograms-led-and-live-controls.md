# M23.4 — Holographic pieces, LED squares and live controls

**Status: checkpoint A complete; B/C specified (2026-10-31).** This is the next presentation
slice after M23.3's moving floor, terminal chess holograms and bracket interface.
The request is for actual playing pieces to resemble projected holograms, squares
to resemble LED panels, and controls to have visible life while idle. The floor
continues scrolling and its arriving lights still reveal chess icons. Do not
replace those animations or remove the main menu's decorative object.

This file refines M23's original glass/crystal direction. It does not claim the
original milestone's optional bloom, physical transparency or sorted glass pass.
The existing meshes, silhouettes, instance transforms, picking and game data stay
in charge. All new effects belong above the engine's float boundary.

## 1. Investigation and integration points

The current implementation, rather than M23's early proposed API, establishes the
following constraints:

- `view::Theme::materials` selects cells, pieces and plinth independently.
  `shaderMaterial` in `src/render/board_renderer.cpp` translates to shader ids;
  id 6 is **turned wood**, despite not being a separate public `Material` value.
  `pieceMaterial` already keys wood variation by type and colour, not position.
- `board.frag`'s id 4 is a faceted crystal with sharp specular and Fresnel.
  That is the source of the gem appearance. Id 3 is opaque glass-like shading on
  ordinary cells, also used for the plinth. Changing id 3 globally would turn
  the plinth into a screen too.
- `board.vert` already exports `fragHeight`, the mesh author's normalized
  foot-to-crown height. It survives instance translation, roll, scaling and
  quaternion orientation. Use it for scanning a piece, including a piece
  standing sideways on a torus. Do not scan world Z or screen Y.
- The shared C++/GLSL push block is 112 bytes: view matrix, light direction,
  camera position, material accent/glow. One additional vec4 makes 128 bytes,
  within Vulkan's minimum guaranteed push-constant capacity.
- `fragLocal` is `inPosition.xy`. This gives ordinary cell-local coordinates,
  but geometry-view cells are patches packed into one identity-instance mesh.
  Their `inPosition` is a sampled world position. Using this varying for an LED
  grid on a curved board would stretch/project across patches and swim on slides.
  The `buildInstances` surface vertex emitter already knows each patch's `(i,j)`.
- `surfaceOpacity` and the portal-rail material expression currently special-case
  `Material::Glass`. They must be reviewed when cells select a different material.
- All menu entries, Start/Back buttons and cycling settings reach `rowControl`
  in `src/render/ui_widgets.cpp`. It creates a real ImGui button and then draws
  a hairline, label, optional tail and instantaneous hover wash/12px text offset.
  No elapsed-time animation exists there. Extend this shared path, including
  keyboard focus, rather than creating another menu widget.
- `Ui::tick` owns `clock_`, field advancement and transitions. Interactive main
  supplies elapsed dt. Capture `renderFrame` intentionally warms the UI with two
  discarded frames and then supplies zero dt. Ordinary clips' `t` is normalized
  move/overture progress; playback uses seconds, and trailer capture uses a fixed
  step. An ImGui backend clock is not a valid source for reproducible effects.
- The interactive event wait is currently 100ms unless a move or attract sequence
  is active. A static board/menu would therefore show the new animation at roughly
  ten frames per second. Its redraw condition is part of this feature.

The existing material tests check dispatch and that an image differs from matte.
They do not check scan direction, control motion, or texture attachment to a curved
cell. Passing those tests alone cannot establish the requested appearance.

Before implementation, save a current-binary baseline: console and manifold standard
board, standard flat board, torus/Klein shape board, menu and library. Capture the
same camera, size and settings intended for the final comparison. Existing captures
under `out/m23/` are useful historical evidence; regenerate a matched baseline if the
current uncommitted interface differs. No new failing test or image is claimed here:
this document specifies the feature and the evidence implementation must produce.

Flat piece decals intentionally remain matte figure colours on the shared token.

icon has crown-to-foot volume. Flat **cells** still get LED shading. Geometry-view
cylindrical icon pieces retain their existing matte icon face too. Record these as
intentional representations, not missing hologram plumbing. Ordinary 3-D pieces,
authored bodies, travelling pieces and capture flourishes use the hologram material.

## 3. One explicit visual-time input

Add `BoardRenderer::setVisualTime(double seconds)` and a `double visualTime_`, default
zero. Negative/non-finite input becomes zero. `record` reduces time modulo 120 seconds
in double precision and converts to float in a new `PushConstants::visual[4]` at offset
112. `visual.x` is seconds; other components are zero/reserved. Both shaders declare
exactly the same trailing vec4. Assert size 128 and offset 112 in C++. All existing
render/record callers remain valid; time is uploaded when recording, not when building
instances. `renderToImage` uses the renderer's explicit time, including its zero default.
No GPU counter, wall clock, random seed or per-frame increment exists in the shader.

Add `Ui::setVisualTime(double)` with the same input sanitation. This affects new
control decoration only, **not** `clock_`, `enter_`, overture progress, either DepthField,
or screen transitions. In `Ui::build`, establish a scoped widget visual-time context
before any cinema/board/menu early return. Expose this small RAII context in
`ui_widgets.hpp` so headless widget tests can supply seconds directly. Its constructor
sets the caller's explicit seconds and its destructor restores the previous value;
default is zero. It contains no clock and no retained animation simulation. Keep it
thread-local or otherwise within the existing single UI-thread convention; do not
share context across independent ImGui instances. `rowControl` only reads that input.

The GUI owns one double elapsed presentation time in interactive main. Advance it
once from the existing measured nonnegative dt, and give the **same value** to renderer
and UI before building/recording each frame. Live theme switches do not reset time.
This clock is not persisted. Shape motion, move progress and camera clocks stay as they
are. No simulation advance is added solely to animate a material.

and a clip frame at visual time 0.5 must match in the effect regions when all other
scene inputs match. Reverse/seeked samples work because evaluation is stateless.

Do not retrofit the existing moving floor's clock in this change. It keeps the prior
capture behaviour and interactive animation. A future explicit background seek can

Update interactive `animating` to include a visible theme with live controls or animated

claiming a hardware framerate from llvmpipe.

## 4. Hologram shading: stable form, descending scan

Replace only id 4's crystal calculation in `board.frag`. Define constants beside the
wood constants; start with these values and adjust only after viewing the artifact:

- Scan period 4 seconds, normalized band half-width 0.055.
- With `p = fract(visual.x / 4)`, centre height is `1.08 - 1.16*p`.
  A smooth band of support 0.055 therefore starts outside the crown, travels down
  through the body, and leaves below the foot before resetting. The reset occurs
  outside the silhouette. Use `fragHeight` clamped to [0,1].
- Use smooth vertex normals for the base form and a subdued cool diffuse term, not
  crystal's derivative facet normal and power-72 specular. Base colour multiplier
  starts at `0.86 + 0.16*max(dot(n,coolKey),0)`; no warm wood lighting.
- Add approximately 28 narrow, static horizontal luminance lines over normalized
  height. Start with at most 8% modulation. They provide the electronic structure
  between passes; they must not erase strips of the piece or alternate alpha.
- Add a restrained view-facing rim (power 3, starting strength 0.12) and a scan
  contribution starting at 0.16, primarily tinted by the piece's own colour.
  At most a quarter of the scan/rim tint comes from `push.material.rgb`. Both armies
  must keep their distinct icy-white and indigo appearance even at the band maximum.
- Filter the fine lines using `fwidth(height * 28)` and fade modulation toward its
  mean as a line becomes subpixel. No screen-space noise; no rapid whole-piece pulse.

Use smoothstep with ordered edges and guard divisions. The scan adds light, never
subtracts the baseline silhouette. The full cycle has no bright flash at reset.
The 4-second period divides the 120-second time wrap exactly. There is no temporal
noise, so still images retain the hologram texture without relying on motion blur.

**Checkpoint A saturation review (2026-10-31):** the existing standard-board
`saturatedPixels(spread=60, floorValue=120)` gate must remain unchanged. A brighter,
smooth hologram base can lift indigo above that threshold over a broad area even
when army contrast remains adequate. The implementation's initial output measured
761 saturated pixels against a limit below 491 in the 256×192 gate. First desaturate
the steady hologram base approximately 35% toward its luminance, consistently for
both armies, retaining luminance rather than making the dark army disappear. Use
that restrained base for the diffuse form; keep scan/rim mostly army-coloured and
at most 20% accent. Review and measure resting and peak-scan phases. If necessary
reduce steady saturation slightly further before lowering brightness. Preserve a
visible icy-white/indigo distinction and keep portal rails the strongest saturated
signal. Do not relax the established gate or remove the contrast assertions.

Keep the already-tested theme colours at first. Passing base-colour contrast tests
does not guarantee contrast after shading: check actual shaded white/black pieces
on both square tones at an unlit phase and the brightest scan phase. If the brighter
indigo army loses identity, reduce additive accent first; do not darken it below the
existing four-combination contrast constraint. Preserve the recognizable crown,
knight profile, bishop notch and pawn head at normal gameplay zoom.

## 5. LED cells attached to their own surface

### Coordinates and vertex layout

Append `float panelCoord[3]{0,0,0}` to `MeshVertex` in `piece_mesh.hpp`:
`xy` is normalized cell UV, and `z` is a coordinate-mode tag. Zero means ordinary
mesh fallback; +1 means sampled panel face; -1 means sampled sidewall. Existing
aggregate initializers receive the zero default. Mesh size changes from 44 to 56
bytes; instance size and layout do not change. Audit every vertex binding and upload
for `sizeof(MeshVertex)`; do not introduce a packed fixed-size copy.

In `buildPipeline`, add location 12 as `R32G32B32_SFLOAT` with `offsetof(panelCoord)`
and raise the attribute count from 12 to 13. The existing binding stride already uses
`sizeof(MeshVertex)`. In `board.vert`, export a new `vec3 fragPanel` at location 10:

- Tag 0: UV is `inPosition.xy + 0.5`, face mask is 1 for normals with
  `abs(inNormal.z) > 0.5`, otherwise 0. These are the cell slab's top/bottom faces.
- Tag +1: UV is `panelCoord.xy`, face mask 1.
- Tag -1: UV may be the edge UV, face mask 0.

Only LED shading reads this new varying. Preserve existing `fragLocal`, `fragObject`,
wood coordinates, seam masking and all old material calculations.

Extend the surface `push` lambda with a panel coordinate argument. For top and bottom
vertices in the `(i,j)` loops use `(j/kSubdiv, i/kSubdiv, +1)`; each patch starts at
(0,0) and ends at (1,1), regardless of cell id, pose, slide, inversion or world axis.
Sidewall vertices in the edge lambda use their corresponding endpoint UV and tag -1.
Each triangle has one tag, because face/side vertices are already separate. Do not
infer screen orientation from a world normal on a twisted surface. The underside
remains an LED face so inside/outside board views both retain checker identity.

### Pixel pattern and lighting

For shader id 7 use a subdued emissive face and dark sidewall, preserving `fragColor`
(including legal-move/last-move/hover tints) and its alpha. The plinth remains id 3.
Start with a 24×24 matrix of neutral LED emitters per cell. Within each pitch the lit
square occupies about 72% of each axis, with antialiased boundaries from derivatives.
The matrix modulates the **existing checker tone**, not a new saturated RGB mosaic.
Use a modest range, approximately 0.82 to 1.04 times that tone, with a narrow inset
bezel at the cell boundary. Do not make every pixel a cyan dot: portal hues must
remain the strongest geometry signal. A faint neutral cool face emission can replace
Lambert shading; sidewalls use the cell's subdued colour and no dot pattern.

Compute derivative footprints before branch-dependent pattern filtering. When a pitch
is under roughly two screen pixels, blend toward the analytic area mean (0.72² for
the square emitter) rather than continuing to resolve dots or using nearest-neighbour
sampling. Fade continuously as the footprint grows; this is essential at oblique
angles and when the board shrinks. No animation is required on LED cells in this slice:
the scan belongs to pieces, while the squares provide a stable electronic substrate.
Avoid global brightness pumping, random dead pixels and colour cycling.

On surfaces, preserve the existing baked seam colours and highlight tints. Ordinary
seam rims still run after material shading. The pixel modulation must not erase a
selected square or change chessboard parity. Do not modify patch sampling or picking.

Use item rectangle coordinates after the button. Other theme paths retain their

use a stable phase offset derived from the ImGui item ID, not drawing order or a random

Clip all new decoration to the item rectangle intersected with the existing clip rect.

console → manifold → console; decorative animation must disappear immediately.

### A test recipe: isolate the actual rook mesh and measure moving light

Use `tests/render/test_offscreen_render.cpp`'s existing `gpu()`, `capturePath`,
`OffscreenTarget::create`, `BoardRenderer::create` and `Image::at`. The raw
`renderer->render` plus `target->readPixels` lambda in “the background callback draws
behind the board, not over it” is the closest reusable readback pattern. Do not use
`renderVariant`: the board, other pieces and perspective would complicate a scan
measurement unnecessarily. Do not add a test-only production mesh API.

**Concrete fixture:**

1. Create one 512×512 target and one renderer, set the manifold theme and leave blur
   off. Make `InstanceSet set{}` with precisely one `Instance body{}`. Set scales to
   `{1,1,2}`, centre `{0,0,0}`, colour `{0.32,0.48,0.66,1}` and material `4.0f`.
   This moderate fixture colour avoids saturated channels hiding added light; real
   army-colour contrast is a separate artifact/dispatch check. Set
   `set.batches[static_cast<size_t>(Archetype::Tower)] = {0,1}` and put the instance
   in `set.instances`; all shadows, flourishes, surface meshes and other batches
   remain empty. `BoardRenderer::create` already uploads the built-in Tower mesh.
2. The actual Tower in `buildArchetype` (`piece_mesh.cpp`) sets `h=0.86` and its
   cone/box emitters store `height=z/h`. Consequently the local height ruler runs
   from world `(0,0,0)` to `(0,0,1.72)` after this scale. Crown boxes extend a little
   past h=1; deliberately restrict measurement to h in [0.08,0.95]. Do **not** use
   a stretched Cell mesh: its stored heights only span about [-0.055,+0.055], so
   scaling it would not create a valid crown-to-foot height ramp.
3. Explicit `OrbitCamera`: target `{0,0,0.86}`, distance `3.2`, yaw `0`, pitch `0`,
   fovY `0.9`, orthographic `true`, roll `0`. This looks from negative Y towards
   the rook and makes normalized height an affine screen direction. Near plane
   stays the ordinary 0.1. Use the full target as board viewport. No UI/background
   callback is needed. Require both ruler endpoints projected with
   `cam.project(point, 1.0f, 512, 512)` to be visible and their separation >200px.
4. Set explicit visual time then render/read images at 0, 0.9, 2.8, 0.9 seconds.
   Check the two 0.9 images are byte-identical. Save baseline/upper/lower PPMs via
   `capturePath` so any failure is inspectable. Clear validation messages before
   rendering and require no validation errors afterward, as nearby tests do.

**Pixel measurement, independent of the shader equation:**

Let F and C be the projected ruler endpoints and D=C−F. For pixel centre P compute
`u=dot(P-F,D)/dot(D,D)` and its perpendicular distance to this projected axis.
These are geometry measurements, not an evaluation of the scan shader. Restrict
sampling to `0.08<u<0.95` and perpendicular distance <18 pixels. The rook's central
shaft is wider than this strip at the proposed resolution. Additionally mask out
background/antialias edges: require baseline pixels in the 3×3 neighbourhood to
have RGB sum at least 30 byte levels above the baseline corner's RGB sum.

For each time T, let `d(P)` be the sum over RGB of
`max(int(imageT.channel)-int(baseline.channel)-1,0)`. The one-byte dead band ignores
quantization differences. Sum d over the strip (E), count pixels with d≥6, and
compute the weighted height centroid `sum(u*d)/E`. Nonzero energy alone is too weak:
start with `E>500` byte-levels and at least 30 changed pixels for each phase. Require
upper-phase centroid >0.60, lower-phase centroid <0.45, and upper minus lower >0.30.
Require at least 75% of upper energy lies at `u>0.55`, and 75% of lower energy at
`u<0.50`. These broad windows encode descending, localized light; they do not pin
an exact centre or reconstruct the easing function. Ratios prevent a whole-body
brightness pulse from satisfying the direction test. If the proposed rendering
constants need artistic adjustment, inspect the saved images before changing these
broad behavioural limits; do not derive limits dynamically from measured output.

At t=0 the specified band is outside the crown, so static scan lines, shading and
rim subtract away. Preserve that explicit resting sample if tuning the implementation.
Compare t=0 and t=4 exactly as an additional repeat check; examine t=3.95 near reset
for no broad change outside the bottom region. Keep the moving phase images visibly
nonidentical to baseline; a permanently dark/no-op material must fail.

**Rotation test using the same fixture:**

Repeat with quaternion `{0,sqrt(0.5),0,sqrt(0.5)}` (a +90° turn about Y). The piece's
local +Z is now world +X, a valid side-of-surface standing direction. Its ruler
endpoints are Fworld `{0,0,0}` and Cworld `{1.72,0,0}`. Change only the camera target
to `{0.86,0,0}`, keep yaw/pitch/orthographic/distance unchanged, and reproject the

this fixture actually turns the scan horizontal on screen. Reuse exactly the same

world Z will illuminate across the shaft instead of moving along it; a screen-Y

This isolates the quaternion/shader contract; existing shape instance tests and the
required torus/Klein artifacts prove the actual surface builder supplies that contract.

Finally change only this fixture's material to 0 and then 6 and confirm pixels are
identical across times for each material. Also retain the actual-console board

Use local test helpers for projection, readback and energy so assertion diagnostics
