# M23.5 — Draw the current HUD on the first replay frame

**Status: implemented, visually reviewed and verified (2026-10-31).** Built after
M23.4's separately committed A/B/C checkpoints. This is a HUD layout bug exposed by A's new still/clip equivalence
check; it is not a material-clock bug or an unrefreshed game snapshot.

## 1. Reproduction and evidence

A saved `standard.cbgame` capture at global time 0.5 seconds differs from the
second frame of a two-frame clip at 2fps, with the HUD enabled. All other inputs
are identical, including explicit visual-time origin 0.25 seconds. The parent
first captured the failure in `build/dev/render-captures/visual-play-still.ppm`,
`visual-play/frame_0001.ppm`, and `/tmp/m23-play-diff.png`.

Independently reproduced with the current checkpoint-A binary, software Vulkan
ICD and validation environment supplied by the parent (`/tmp/m23-env.sh` locally):

```bash
./build/dev/src/gui/endspielzero_gui --play tests/data/games/standard.cbgame --theme manifold --width 640 --height 400 --visual-time 0.25 --play-at 0.5 --shot /tmp/m23-hud-still.ppm
./build/dev/src/gui/endspielzero_gui --play tests/data/games/standard.cbgame --theme manifold --width 640 --height 400 --visual-time 0.25 --clip /tmp/m23-hud-clip --frames 2 --fps 2
```

Both commands exit zero with validation enabled. Comparison of the still and
`/tmp/m23-hud-clip/frame_0001.ppm` finds **1,038 unequal RGB pixels**:

| Region | Unequal pixels | Inclusive bounding box |
|---|---:|---|
| Top-right turn label | 884 | (504,25)–(617,34) |
| Bottom-right recent moves | 154 | (584,368)–(617,376) |
| Everything else, including board | 0 | — |

The still already says **BLACK TO MOVE**, `ply 1`, `20 legal`, and shows the moved
piece. Its first recent-move row is absent. The clip frame has the same current
turn label with slightly different positioning, plus `1. e2e4` in the bottom-right
ledger. Converted inspection images are `/tmp/m23-hud-still.png` and
`/tmp/m23-hud-clip.png`. These temporary files are evidence, not dependencies for
permanent tests. The existing checked-in game fixture is the permanent input.

## 2. Actual cause, and why tests missed it

The data is current before the frame is built:

1. Capture `renderPlayFrame` in `src/gui/main.cpp` calls `GameRunner::step` until
   the requested playback cursor is applied, then states the move/shape pose.
2. `GameRunner::step` (`src/app/game_runner.cpp`) calls
   `Session::playMoveText`; that path commits the game move and calls
   `refreshSnapshot` and `refreshTemporalView` before returning.
3. `Ui::buildGameHud` (`src/render/ui.cpp`) reads `session.game()` directly for
   result, side to move, ply count, legal moves and moveHistory. It does not read
   a stale string cache or derive these labels from the board snapshot.

The two discrepant windows share a layout dependency:

- `##status` and `##recent` use `ImGuiWindowFlags_AlwaysAutoResize`.
- Each supplies a right-hand pivot to `SetNextWindowPos`; recent moves additionally
  use a bottom pivot. Current text is then right-aligned against
  `GetContentRegionAvail`, whose width came from the window's current/previous
  size rather than a measurement of all the current rows.
- Capture's two discarded warm-up frames occur **before** the real playback step,
  after the runner has reset to the initial position. They size the WHITE status
  label and do not open `##recent` because plyCount is zero.
- A standalone still applies e2e4 and draws that new HUD once. A clip applies e2e4
  for frame zero and draws it again for frame one; ImGui has a frame of current
  content measurements, and its newly auto-sized recent window is now visible.

Thus the problem is previous-frame auto-sizing/first-appearance layout. Adding
another `refreshSnapshot`, reapplying a move, advancing animation, or modifying
playbackCursor cannot repair it. The correct current text is already present in
the still, which also rules out a turn-data lag.

The existing playback clip gates are cinema captures, so there is no HUD to compare.
The prior determinism test compares two clips with the **same frame history**.
HUD screenshot smoke tests check exit status/validation, not first-frame equivalence
to the same state reached with another render history. Checkpoint A's visual clock
comparison exposed the missing property; its cinema comparison should remain a
separate material-time regression, not be weakened or repurposed to hide this issue.

## 3. Minimal correction: measure these text overlays before Begin

Change only the noninteractive text layout of status and recent moves in
`Ui::buildGameHud`. Extend the established `CalcTextSize`/right-alignment pattern
and explicit pre-Begin sizing used by `widgets::beginPlate`; do not introduce a
new UI renderer, layout pass, data cache or replay model.

### Prepare current rows once

Immediately before each affected window, assemble its current visible rows, fonts
and colours. A small file-local type in `ui.cpp` is sufficient:

```
HudTextRow { std::string text; ImFont* font; view::Rgba colour; }
```

Do not add this type to app/session state. Use exactly the existing labels and
formatting, in exactly the existing order:

- Status: current side/result in display font; ply/legal line in small font;
  optional end reason or IN CHECK in small font.
- Recent: last min(history.size(),6) moves in small font, with the current
  `%2zu%s %s` text and the existing last-row accent. Keep the zero-ply condition.

Construct each string once, then use that same string/font for measuring and
rendering. A status line must not be independently formatted in two branches.
No history notation, result semantics, colour roles or fonts change.

### Measure and anchor from this frame's contents

For each row, push its font when non-null and call `ImGui::CalcTextSize` using the
same font context as `TextUnformatted`. Store its width and line height. Compute
content width as the maximum row width, and content height as the sum of row
heights plus `(rowCount-1)*spacingY`. Status uses the existing current style item
spacing; recent moves use its existing `px(1)` spacing. Empty rows, if ever present,
reserve one current-font line height rather than collapsing the row.

Before `ImGui::Begin`:

1. Retain zero window padding, as currently used for both windows.
2. Set the exact current content size with `SetNextWindowSize(..., ImGuiCond_Always)`;
   clamp each component to at least 1 pixel for valid ImGui geometry. Handle
   ImGui's WindowMinSize explicitly: push a local small minimum (1,1), or include
   the existing minimum in the measured outer size. Choose one policy and use it
   consistently in the test's expected right/bottom anchors. Prefer the local
   minimum so short rows do not acquire unrelated empty height.
3. Retain the existing viewport WorkPos/WorkSize and px(22) margin anchors and
   pivots `(1,0)` for status, `(1,1)` for recent. Remove AlwaysAutoResize **only**
   for these measured windows; do not change shared overlayFlags for the variant,
   controls, FPS or other windows without evidence they need this fix.
4. Begin the window and render the prepared rows right-aligned to its known current
   content width. The existing rightAlign pattern can remain, but use the prepared
   widths and ensure each new row starts at the same content-left origin before
   adding its own width difference. Preserve normal ImGui text item submission.
5. End and balance all font/style pushes, including the local minimum-size change.

A small file-local shared helper for these two windows is appropriate; a new public
widget API is not required. If a helper is extracted for tests, it must be the one
used by both production call sites, not a duplicate mock layout formula. Do not
switch this into raw global draw-list text just to bypass window sizing: normal
clipping and the existing noninteractive window behaviour should be retained.

Explicit dimensions are known before Begin, so both right/bottom positioning and
first appearance can be correct immediately. Remove neither the global two capture
warm-ups nor the frame-time pinning: those serve other pane transitions and layout.
Do not add an extra rendered/hidden frame per playback sample. That would hide this
particular symptom, spend GPU work, and keep interactive first-frame layout wrong.

### Invariants and edge cases

- Same current game, viewport, theme, UI scale and visual time produce the same HUD
  text geometry regardless of the previously rendered game state or number of frames.
- WHITE→BLACK and BLACK→WHITE may change the left edge of the status block, but its
  right anchor stays at the configured viewport margin on the **first** changed frame.
- Recent rows appear on the first frame with plyCount>0, grow through six rows and
  shrink/disappear on undo/reset without one frame using the old bottom pivot.
- Check/end-reason rows take effect in the same frame. Changing status height must
  not leave text clipped by an older window rectangle.
- Scale all existing spacing/margins through px; measure actual active fonts after
  the theme/scale is applied. Font fallback remains supported.
- Keep label contents, move notation, keyboard/pointer input routes and action
  buttons unchanged. Do not change window input flags as an accidental part of sizing.
- Long labels may occupy more width; this fix is not a new text-wrapping/responsive
  design task. At supported capture sizes all current status/recent rows must fit.
- No clock, replay step, camera or material computation changes. Presentation-only
  geometry remains in render; no engine/app data-format change or ADR is necessary.
