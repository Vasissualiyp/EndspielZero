# M23.7 — Bounded manifold buttons with hover glitches

**Status: implemented, visually reviewed and verified (2026-10-31).** Built after
M23.6 was verified and committed (`f8d6172`). The user's review supersedes M23.4 C's visual direction:
“a little line running through the text” does not make the menu feel like a game.
They want glitchy hover feedback and buttons constrained horizontally instead of
stretching to the right edge. The independently observed text-overlay focus trap
is deferred; do not combine that input fix with this visual slice.

## 1. What is there, and what to extend

Reviewed the actual `rowControl`, `menuEntry`, `button`, `cycleButton` and `beginPane`
implementations in `src/render/ui_widgets.cpp`; their call sites in `ui_menus.cpp`;
the current control tests; and `out/m23/controls/controls-review.png`. A fresh
1280×720 capture at visual time 0.3 is `/tmp/m23-glitch-baseline-menu.ppm` (converted
for inspection to `/tmp/m23-glitch-baseline-menu.png`). It exits validation-clean.

In this capture, main-menu rows start around x686 and run to x1234: **548 pixels**
of mostly empty rule around a short label. `Ui::buildMainMenu` passes all of
GetContentRegionAvail().x as the width to menuEntry. Pause, Tutorial/Welcome and
editor home use the same pattern. `rowControl` draws the shared top rule and a
28-logical-pixel segment moving once every six seconds, plus a weak hover wash.
The right side never visibly terminates as a button. The ground's bright moving
lines are also visible through the transparent controls, which weakens the label
area's separation from the scenery.

Use the existing shared control, not per-screen duplicate widgets. It already has
real ImGui input, disabled-state handling, explicit visual-time input, mono action
fonts and focus/held state. The new treatment applies to manifold through
`Theme::liveControls`; console preserves its existing draw path and widths.
No game engine, GPU shader, render pass, material, background or camera changes.

The technical time/input work from M23.4 C remains useful; its idle travelling
rule and corresponding idle-motion expectations are deliberately replaced here.
The menu floor must still scroll, lights must still reach chess-icon terminals,
and pieces/LED squares keep their existing materials. Do not freeze the entire
screen just because its idle buttons become quiet.

## 2. Visual contract: a finite control, then a local signal glitch

The settled manifold control has a visible, finite dark plate with an open,
segmented frame. It looks selectable before hover, but does not animate while idle.
On hover or keyboard focus, the frame brightens, two small horizontal fragments
misregister briefly, and thin copies of the label shear sideways behind its intact
text. This is localized digital interference, not a full-row flash, random glyph
replacement or moving hitbox. The label is always readable and remains at the same
position. Pointer hover and visible keyboard focus receive the same treatment.

Starting values (tune against the artifact, not just a vertex-count test):

| Element | Idle | Hover / visible keyboard focus |
|---|---|---|
| Plate | theme.panel at 0.68 alpha | theme.panelHi at 0.86 alpha |
| Main edge | theme.interfaceRule at 0.60 | theme.boneDim at 0.90 |
| Corner/terminal accent | subdued theme.boneDim | mostly theme.bone, slight theme.ember tint |
| Main label | existing readable role colour | same stationary role, brighter only if needed |
| Label-slice echoes | none | 0.16 quiet / 0.38 burst alpha |
| Glitch fragments | none | short pieces of frame/background only |

Keep the palette cool and mostly neutral. For glitch tint use approximately
`mix(theme.bone, theme.ember, 0.20)` and a dim neutral companion. Do not add red/green
RGB channel splits, rainbow flashes, saturated magenta, or seam-ramp hues. Portal
colour should still communicate topology rather than control noise. Existing primary
and cold roles remain recognizable; the plate does not flatten all roles to white.

A small chamfer at the upper-right/lower-left corners (6*scale, clamped to a fraction
of the row height) is appropriate. Use a simple convex polygon and short corner
strokes. An ordinary rectangular plate with deliberate corner breaks is an honest
fallback if the chamfer complicates clipping. The important properties are a clear
right end, a dark backing under the text, and a perceptible response to hover.
Do not apply a full bright rectangular border to every idle row.

The pressed state adds a fixed inset corner and slightly brighter backing; it must
not translate or resize the label/plate. Disabled controls keep the same footprint
with subdued static text/frame, no glitch echoes, no travelling segment and no
activation. The focus marker is steady and distinct even between glitch bursts.

## 3. Geometry and width: change the layout once, never on hover

### Menu rows

Constrain all manifold `menuEntry` rows in the shared function. The four sets of
callers are main menu, pause, Tutorial/Welcome and editor home. Their supplied width
means available layout width; console retains its current interpretation.

Let A be max(0, min(supplied positive width, GetContentRegionAvail().x)), with available
width used when no positive width was supplied. Let s be the supplied scale. Start
with a preferred cap of **320*s**. Reserve a right gutter of **24*s** when A is at
least **200*s**; below that reserve **min(8*s, 0.04*A)**. Final width is
`max(1, min(320*s, A-gutter))`. No minimum of 200/240/320 may override the available
width. The threshold only chooses gutter generosity. Thus even a pane narrower
than the cap has a deliberate right gap where feasible; a 1-pixel edge case remains
valid rather than producing negative geometry.

Keep the existing left alignment with the heading/content. The real ImGui::Button
receives this bounded width, and every plate, tail, hover region and clip uses its
actual item rectangle. Do not merely shorten the drawn rule while leaving the whole
pane clickable. The user should be able to point/click to the right of the plate
without selecting its action. Row width/height and glyph positions are independent
of visual time, hover, focus and press; resizing or changing UI scale can relayout.

### Text within a bounded row

Prepare label/tail geometry **before creating the ImGui item**. Use the actual label
font and size, not character counts or an assumed pixels-per-letter. Preserve full
button captions on supported layouts:

1. Keep current 36*s menu label inset, number and tail when they fit with at least
   12*s between label and tail and 12*s right padding.
2. If that would squeeze the main label, omit the decorative row number and use
   12*s left padding. An enabled row's arrow may also be omitted; it is decoration,
   not an action name. Do not silently remove a disabled row's “NOT BUILT” state.
3. Wrap the main label at words to the remaining bounded width if needed. Use
   ImFont::CalcTextSizeA's wrap width and the same wrap width for AddText. Minimum
   height remains 42*s; otherwise height is measured label height plus 16*s vertical
   padding. A disabled status tail that cannot fit alongside goes on a separate
   small-font line below, included in the height.
4. Long unbroken labels follow ImGui's measured character wrapping rather than
   expanding the item offscreen. No active-state-dependent wrap or font shrink.

Menu panes already scroll vertically when their contents exceed the viewport.
Let additional wrapped row height feed the existing beginPane/endPane measurement;
do not restore a fixed menu height or hide lower actions. Test a long real Tutorial
entry (“Show me all the boards”), not only “Play”. At extremely small widths the
window's clipping remains authoritative; document that a physically tiny viewport
cannot display an arbitrarily scaled label, rather than inventing a minimum that
moves the control offscreen.

A small file-local `ControlLayout` measurement helper is appropriate. It should
hold width/height, label position/wrap width, optional index/tail positions and the
actual rendered label lines; rowControl uses that single result for both its item
size and drawing. It is presentation data, not persisted state or a new app model.
Do not create a separate menu input implementation merely to support wrapping.

### Compact buttons, values and action pairs

Existing explicit-width buttons in the HUD already are compact. Give them the new
plate/glitch treatment **without widening them to 320*s**. Keep their explicit widths
and one-line layout wherever the current content fits. A zero-width action should
measure its visible caption plus padding; a zero-width cycling control must measure
both label and value. Do not let hidden IDs determine a zero-width item's size.

Cycling settings retain their full value and label. Use the same measurement helper
to put the value on a second line if it cannot fit beside the label within an
explicitly constrained width, and grow the item height accordingly. Do not conceal
values with a hard clip or an ellipsis just to make a cap pass. The existing settings
body is a scroller, so taller rows can use it. Callers with deliberate compact widths
remain compact; this is not a blanket change making every slider/checkbox a card.

For menu **footer** pairs that are explicitly laid out SameLine (library START/BACK,
watch START WATCHING/BACK, settings BACK/RESET TO DEFAULTS), plan the pair from the
available footer width before reserving body height:

- Keep the current preferred widths when both fit, with the ordinary item spacing
  and a small right gutter. Do not change a working 1080p/3× row unnecessarily.
- If preferred widths do not fit but both measured one-line captions plus padding
  do, use those compact measured widths.
- Otherwise stack the two buttons, each bounded by available width with the small
  gutter and measured wrapping. Reserve the sum of both actual heights plus their
  spacing **before** creating the scrolling body. Do not call SameLine for the
  second item in this case.

Use one small shared pair-measurement helper with the same ControlLayout rules;
callers draw the actions they already own and retain their IDs/callbacks. Modify
only the relevant layout blocks in `Ui::buildNewGame`, `buildWatch` and
`buildSettings`; single-action footers need only their current bounded button.
Preserve the library's existing invariant that START/BACK are outside its body
scroller. A body minimum height must never force the footer out of view; clamp the
remaining body space to at least one pixel, as the repaired library already does.
If an entire two-button footer exceeds the viewport at extreme scale, allow the
outer existing pane to scroll, rather than placing its second action outside its
window with no way to reach it.

This is the bounded responsive work required by narrower buttons. Do not change
the 50/50 shell split, decorative object placement, global scale policy, all editor
panes or the game's HUD layout as unrelated improvements.

## 4. Deterministic glitch algorithm and draw order

Remove the old six-second travelling top-rule segment from the live-controls branch.
Idle manifold controls must be byte-identical at different explicit visual times
when the rest of their state/inputs match. Console keeps its existing path unchanged.

When `usable && (hovered || focused || held)`, read the existing scoped explicit
visual-time seconds. Default remains zero. Use the existing item ID as stable seed;
never use frame count, global random state, backend GetTime/DeltaTime, pointer speed,
wall time, the game's move clock, or a timer that must be advanced by a prior frame.

A concrete starting algorithm:

- Derive phaseOffset in [0,1.2) from a fixed integer hash of ImGui item ID. Reduce
  explicit time in double precision before converting to float. Period is 1.2s.
- Within each period, strong glitch windows are [0,0.16] and [0.30,0.38]; use a
  short smooth envelope at their ends. Outside them the hovered/focused plate
  retains a very faint sliced echo and its steady focus/hover frame.
- Sample deterministic steps at 8Hz (`floor((seconds+phaseOffset)*8)`). Hash that
  integer and item ID for two signed horizontal offsets in [-3*s,+3*s]. Outside
  a strong window clamp offset magnitude to 1*s and lower echo alpha to 0.16;
  during a strong window use up to 3*s and 0.38 alpha. This provides immediate
  localized motion on hover without waiting for the larger burst to begin.
- Choose two horizontal slices through the primary caption, centred near 0.30 and
  0.70 of its line height. Each slice is at most 2*s high and at most 12% of the
  glyph-line height. Total disturbed area is small. For wrapped labels choose one
  line per burst from the ID/step; do not glitch every line simultaneously.
- Draw offset copies of the exact original caption, same font/size/wrap, clipped
  to those slices and the label region. One is cool-neutral; the other is dimmer.
  They are **echoes behind an intact main label**, not replacements of glyphs.
- Add at most two short displaced fragments along the plate's side/corner bands,
  8–22*s long (clamped to plate dimensions), with the same time-derived offsets.
  Fragment strokes/background blocks stay outside the main label/tail interior;
  no solid horizontal line passes across the caption. Limit fragment brightness
  and area so the response reads as interference rather than a blinking frame.

The actual readable label is drawn last, once, without jitter, clipping damage or
content substitution. The row number and current setting value remain stable and
are not glitched. The disabled state never reaches this algorithm. Avoid full-label
copies separated by large offsets: that makes ordinary double vision rather than a
local signal fault. Avoid turning the whole plate on/off eight times per second.

Draw order in rowControl: real input item → derive actual rect/state → plate backing
→ fixed frame and focus/held marker → sparse frame fragments → sliced label echoes
→ intact index/label/tail. Clip **all** new decoration and text to the item rectangle
intersected with the current draw-list clip rect; echo slices additionally intersect
the measured label region. Because beginPane widens clipping during transitions,
explicit item clipping is necessary. Preserve its existing transition transform at
endPane; do not transform hitboxes to chase the drawing or move the ImGui cursor
when emitting decoration.

The visible glitch must be strong enough to see in a hovered still and in a short
live hover. The numerical values above are starting bounds, not a justification for
shipping an effect the user can barely see. Tune offset/alpha/fragment size within
the readability/area limits after reviewing full-size screenshots.

## Implemented and reviewed

The shared real Button now uses measured manifold control geometry. Menu entries
cap at 320 logical pixels with a responsive right gutter; compact actions retain
their supplied width. Main captions, disabled status and cycle values wrap based on
their actual font. Footer pairs preserve preferred widths, compact or stack, with
height reserved before the body. Narrow manifold menu padding makes room for text;
editor home uses the same relief while designer pages retain their original padding.

scrolling, preventing a new scrollbar from narrowing already-measured controls.

adds two CPU-clipped label-slice echoes and short stepped frame fragments, derived
only from scoped presentation time and the stable item ID. The intact caption,
index and value remain last and fixed. Disabled controls emit no moving effects.
Parent-row transition scissors now follow the same transform as their vertices;
full-viewport scissors stay fixed. Existing child-window transition behavior is
unchanged. Console keeps its original input/drawing/layout path.
