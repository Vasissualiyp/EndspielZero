# M23.6 — Gameplay shortcuts must survive idle HUD navigation focus

**Status: implemented, visually reviewed and verified (2026-10-31).** Built
after the M23.5 HUD fix was verified and committed (`3913e9c`). This is a separate input
ownership bug; neither the recent HUD measurement fix nor manifold's animated
control drawing should be rolled back to repair it.

## 1. Reproduction, including the actual consumed event

The parent reproduced this twice under Xvfb at 1280×720, using an isolated settings
file containing `theme = manifold` and `flat_view = true`, with hot seat off:

1. Click e2 at approximately (666,498), then e4 at (666,386).
2. The title/HUD show Black to move, ply 1.
3. Focus the game window explicitly and press `u` with a 150ms key delay.
4. The game stays at Black/ply 1.
5. Click UNDO at approximately (50,658); it immediately returns to White/ply 0.

Parent evidence lives in `out/m23/hud/live/` and
`/tmp/m23-hud-live-focused.py`. The investigation independently repeated the sequence
with the existing binary, the software Vulkan environment from `/tmp/m23-env.sh`,
an Xvfb window and **a debugger breakpoint at the SDL key-down capture gate**.
No production source was edited for this experiment. The standalone investigator
was `/tmp/m23-key-investigate.py`; debugger commands were
`/tmp/m23-key-capture-original.gdb`.

For the real `u` event, the debugger observed:

```
key=117  consumed=1  WantCaptureKeyboard=1
NavActive=1  NavVisible=0  WantTextInput=0  ActiveId=0
```

The key is delivered correctly by X11/SDL. It is discarded by `if (consumed) break`
before the Undo action switch. No text field is editing and no widget is active;
only keyboard navigation readiness causes capture. Pointer undo takes a separate
path through the same session action and succeeds.

The parent saw Escape pause/resume work in an earlier run. In the instrumented
sequence Escape also reached the capture gate with consumed=1 and therefore did
not reach `shell->back`. Window title alone cannot establish whether a pause menu
opened. Treat Escape as a required live regression, not as proof the blanket gate
works reliably for other keys.

A second debugger-only experiment set
`GImGui->IO.ConfigNavCaptureKeyboard = false` before each UI NewFrame. The real
`u` event then had `consumed=0, NavActive=1, ActiveId=0` and successfully undid e2e4.
Opening F12's console and typing `u` still produced
`consumed=1, WantTextInput=1, ActiveId!=0`; text ownership was preserved. This is
proof of the narrow capture distinction, not a production implementation or a
complete regression test. The experimental logs are `/tmp/m23-key-gdb.log`.

## 2. Actual path and why existing tests missed it

`Ui::create` in `src/render/ui.cpp` enables ImGui keyboard navigation.
`ImGuiIO::ConfigNavCaptureKeyboard` defaults true (documented in the installed
ImGui 1.91.4 public header), which sets WantCaptureKeyboard whenever navigation is
active. Navigation can be active with an invisible focus marker, no ActiveId and
no text input, exactly as observed above.

`Ui::processEvent` always feeds `ImGui_ImplSDL3_ProcessEvent` first, then returns
`io.WantCaptureKeyboard` for key-down, key-up and text-input events. The interactive
loop in `src/gui/main.cpp` discards a consumed key-down before it can reach:

- hot-seat `Session::feedHotSeat`;
- Escape/back and the menu's Q shortcut;
- U/R/F/G and the geometry brackets;
- trailer/keyframe keys.

The existing trailer-specific policy in `Ui::build` already acknowledges this
conflict: it disables NavEnableKeyboard during attraction so Space belongs to the
trailer instead of activating a focused UI button. Normal gameplay re-enables nav
and therefore inherits its whole-keyboard capture default.

This predates the current visual work. `git blame` traces the processEvent/capture
return to `f968adc` and the trailer exception to `313b1bf`. Commit C (`efeb5d5`)
only observes IsItemFocused/NavVisible/IsItemActive for drawing and retains the
actual Button and IDs. M23.5 changes status/recent text measurement, not the SDL
key switch. An old-binary rebuild is not needed to justify changing the demonstrated
capture boundary, and was not performed during this investigation.

Existing app tests invoke Session actions or HotSeat directly, bypassing SDL and
ImGui. Widget navigation tests inject ImGui key events and assert button focus/
activation, bypassing the main loop's `consumed` gate. Screenshot `--ui-click
key:...` injection also enters the ImGui path rather than the interactive SDL key
switch. Consequently each subsystem can be green while their input boundary
silently discards a valid gameplay shortcut.

## 3. Small correction using ImGui's existing ownership switch

### Disable navigation's blanket capture, retain actual UI ownership

In `Ui::create`, beside the existing NavEnableKeyboard setup, set:

```
io.ConfigNavCaptureKeyboard = false;
```

Document the distinction: navigation still receives all SDL events and remains
usable, but idle navigation focus does not reserve **every** key from the app.
Active widgets, text editing and modal windows must continue to set capture normally.
Do not substitute `WantTextInput` as the only capture rule: sliders, held buttons,
modal confirmations and other non-text UI interactions also need ownership.

Keep `Ui::processEvent`'s backend call and its return of WantCaptureKeyboard.
Keep main's consumed-key gate. Do not add an exception such as “always undo on U,”
which would undo while typing into the console or a filename. Do not bypass capture
when a modifier is held, infer ownership from theme/colour, or clear ImGui focus on
every board click.

Use the setting consistently at UI-context creation rather than toggling it between
menu and game inside `build`. That avoids inheriting the menu's previous-frame
WantCaptureKeyboard at the first game event and uses a public ImGui control intended
for precisely this distinction. Existing application branches already scope U/R/F/G
to gameplay; ordinary menu arrow/Tab/Enter handling remains ImGui's, and the main
switch does nothing with those keys outside its existing trailer branches. Q on the
main menu and Escape/back may now reach their already-authored app handlers when
only nav focus is present; that is intentional. A text box or modal must still block
them. Do not invent new menu shortcut bindings.

This is a capture-policy change, not removal of keyboard navigation. Keep normal
single-player HUD buttons navigable with Tab/arrows and activatable with Enter/
Space, including C's stationary focus marker. A key must not activate a UI control
and an app command at once. The current normal-game bindings do not assign an app
action to Enter/Space; retain that separation. Trailer mode retains its existing
exclusive navigation policy and key bindings.

### Preserve hot-seat key ownership, especially Tab

HotSeat's white cancel key is Tab (`src/app/hotseat.hpp`), and its black cancel key
is backslash. Merely disabling nav capture while leaving Tab navigation active would
let Tab both cancel partial board entry and move HUD focus. The existing feed order
in main is necessary but insufficient because the event has already been queued for
ImGui before that branch runs.

Extend the **existing** navigation-policy block in `Ui::build`, rather than adding
another key router:

- Normal single-player game and menus: NavEnableKeyboard remains on.
- Attract/trailer: retain the current nav-off policy unchanged.
- Ordinary Game screen with an enabled hot-seat session and no pending promotion/
  move-confirmation modal: turn NavEnableKeyboard off. The keyboard belongs to the
  players' coordinate entry and cancel keys. Pointer HUD controls remain usable.
- A pending promotion or move-confirmation modal: permit keyboard navigation for its
  choices; modal capture must prevent board entry/Undo/Reset behind it. Once dismissed,
  the ordinary hot-seat policy resumes on the next frame.
- Menus/settings outside the Game screen restore normal navigation even if the
  underlying saved session has hot seat enabled.

Base this on the actual screen/session/pending state, not `Theme::liveControls`.
Read the existing `pendingPromotion()` and `pendingMove()` accessors. Text editing
continues to capture with navigation disabled, as the existing trailer case already
requires; F12's console must remain editable in either mode.

Do not change `Session::feedHotSeat`, keyChar, the players' key tables, the
`twoPlayer` guards on U/R/F/G, or hot-seat game rules. The wrong player's keys remain
ignored/consumed by the existing HotSeat machine. The keyboard user can still pause
via Escape when no field/modal owns it; the menu then regains normal navigation.

If implementation finds hot-seat Tab still traverses a widget because the policy is
applied too late, prove the timing in the failing event test and move the **same
policy preparation** before the next NewFrame using the established UI frame setup.
Do not solve that timing by skipping backend event delivery or introducing a second
copy of the game's keyboard map. Explicitly test normal Game→hot seat→menu transitions
with a completed frame between state changes. Same-event-batch screen transitions
must not dispatch two app commands or leak into a text/modal owner.

### Scope and non-goals

Expected production changes are in `src/render/ui.cpp` and explanatory UI interface
comments only if needed. Main's existing key mapping and action switch should remain
unchanged unless a failing boundary test proves another issue. No new action enum,
engine changes, settings migration, shortcut customization system or new input layer.
Do not change key repeat, modifier behaviour or existing shortcut assignments in this
slice; they have separate semantics. Tests should use nonrepeat key-down/up pairs.
No new ADR is needed for using the existing UI library's capture configuration and
extending the already-present navigation policy.

## 4. Test-first regression that reaches the real boundary

### Failing SDL-event/UI test

SDL window, `Ui::create`, Shell/Session and controlled-frame fixtures. A newly
separate test file is unnecessary. Give the case a distinct `[keyboard-routing]`
tag plus `[render]` and any device tag needed by Ui::create.

1. Build the real standard Game HUD with a real UI context, settle normal screen
   entry, then make e2e4 through the real session. Use normal frame boundaries and
   release any input. Establish an idle navigable HUD: at least one HUD window is
   focused, NavActive=true, no text field is active. Do not force WantCaptureKeyboard

   `Ui::processEvent`, build frames, then release it; a focused but inactive button

   focus visible. Idle navigation must not swallow U/R/F/G/brackets solely due to
   focus. Normal keyboard navigation still works: Tab changes focused item and
   Enter or Space activates the focused HUD button once through the real widget.
   Use an action with a measurable result (Undo) and a known starting ply count.
4. Repeat for both themes. No material time or capture warm-up trick should affect
   the returned ownership result.

This test intentionally verifies the changed production boundary rather than copying
main's action switch into the test. The live end-to-end test below verifies that main

forcing consumed=false proves neither boundary and must not replace these checks.

### Genuine UI ownership must remain intact

In the same real UI harness, open the actual F12 console via its ordinary key path
and wait for its InputText to be active. Send KEY_DOWN U plus SDL_TEXTINPUT `u`,
then KEY_UP, all through processEvent with normal frames. Require the key-down to
be captured, the console text to accept the character, and the game ply to remain
unchanged. Close the console through its existing toggle and demonstrate delivery
returns after focus has cleared. Do not fake the test by assigning io.WantTextInput.

Cover a real promotion or confirmation modal: while visible, U/R and board-owned
hot-seat letters must be captured and game state unchanged; Tab/arrows/Enter must
still select/activate an allowed modal choice. Use an existing setup/FEN fixture,
not new campaign content. Cover a held/active control or slider if the fixture makes
one available: changing nav capture must not globally force processEvent=false.

For hot seat, use actual session configuration and UI policy, send coordinate letters
and Tab cancel through SDL events, and confirm the capture boundary allows those keys
on the ordinary board without moving HUD navigation focus. Existing app tests already
prove coordinate meaning and wrong-player rejection; retain them. Verify pending
modal navigation and pause/menu navigation regain ownership as specified above.
Retain the existing trailer Space/arrow/Enter/Delete tests or add equivalent boundary
coverage where absent; ordinary keyboard navigation must not activate a trailer
button concurrently with its app command.

The currently tested renderer/UI cannot execute the entire main loop. Do not claim
full real-input correctness from an ImGui event test alone: the following live check
is required for acceptance.

## 7. Timing addendum from implementation review (2026-10-31)

The first implementation's settled modal tests pass, but a debugger on the actual
compiled `[keyboard-routing]` test proves a one-frame modal-ownership gap. At the
first successful `BeginPopupModal("confirmmove")` body, frame 9 reports:

```
WantCaptureKeyboard=0  NavActive=1  ActiveId=0  WantTextInput=0
OpenPopupStack.Size=1
```

Frame 10 reports WantCaptureKeyboard=1. Both themes reproduce the same sequence.
Evidence: `/tmp/m23-modal-timing.gdb` and `/tmp/m23-modal-timing.log`. No shared source
or test file was edited for this experiment. This follows actual frame ordering:
NewFrame computed IO capture before buildGameHud opened the modal. The main loop
can receive another key before the next NewFrame updates that flag. Session Undo/
Reset do not provide a second modal guard: they can clear pending state.

### Current popup ownership augments the existing capture query

Keep ConfigNavCaptureKeyboard=false and the backend event flow. Strengthen
`Ui::capturesKeyboard()` to return the disjunction of:

1. the existing `ImGui::GetIO().WantCaptureKeyboard`; and
2. a currently open modal from ImGui's actual popup hierarchy.

Use `ImGui::GetTopMostPopupModal() != nullptr` (the existing pinned ImGui internal
API). `ui_widgets.cpp` already uses imgui_internal.h for narrowly scoped UI state;
include it in ui.cpp for this one hierarchy query. Do not use
GetTopMostAndVisiblePopupModal: initial sizing/hidden frames must still own input.
Do not scan all windows' Active/WasActive flags: a modal closed this frame may
remain in that list, and a stale window flag must not trap the keyboard. The
current open-popup stack expresses the ownership that is needed.

In `Ui::processEvent`, after forwarding to ImGui_ImplSDL3_ProcessEvent, have all
keyboard/text event cases return **capturesKeyboard()**, not a parallel expression.
The public getter and real SDL dispatch result must never disagree for the same
state. Mouse capture remains unchanged. Do not set WantCaptureKeyboard manually,
call NewFrame from processEvent, force modal capture permanently, or special-case
U/R to bypass another owner.

This addresses the demonstrated interval after a modal is opened by UI construction.
It does not introduce a second event router or claim all hypothetical same-batch
app transitions have been audited. The actual app's pending state and popup
lifetime must still agree in the tested normal-frame interaction sequences.

### Recompute navigation policy after UI actions

Extract the existing navigation-bit calculation into one file-local helper taking
the current Shell (or an equivalent private Ui helper). Call it at the start of
Ui::build as now, **and immediately before its normal final return**, after the
screen builder and drawCheckEdges. A modal's PLAY/CANCEL/promotion choice, menu
resume or settings change may have changed session/screen state during that build.
Applying the same helper again means the next ImGui NewFrame sees the correct
hot-seat/trailer/menu policy before it processes queued Tab/Space events. Do not
copy the conditional into two separately maintained blocks. Cinema's early return
has no interactive action and needs only the initial application.

In particular, a hot-seat confirmation modal may close during buildGameHud. If the
policy is only applied before building, NavEnableKeyboard remains on for the next
NewFrame and an immediate Tab can navigate the HUD in addition to being a player
cancel key. The final policy application removes that double ownership.

Do **not** clear io.WantCaptureKeyboard on modal close. It can still represent a
held activation key, an active button/text field, or the previous completed frame's
modal capture. Retain conservative capture until the next normal NewFrame refreshes
it; this can swallow an event during the modal-release boundary. That bounded,
documented conservatism is preferable to dispatching a release/activation sequence
into gameplay. It must clear after one ordinary frame with no active owner, and
must never remain latched merely because the old modal window still exists.

### Add assertions before the settle helper hides the interval

Extend the real SDL/UI tests with explicit single-frame boundaries:

- After establishing pending confirmation/promotion, build exactly one frame.
  Require capturesKeyboard=true and require processEvent(U), processEvent(R) to
  report capture **before** another NewFrame. Check actual game/pending state is
  unchanged. Record io.WantCaptureKeyboard for diagnostics; it may still be false,
  proving the test exercises current popup ownership rather than settled IO.
- For each keyboard/text event tested, assert processEvent and capturesKeyboard
  agree. Keep SDL key-up delivery balanced and do not synthesize another UI frame
  merely to make the first assertion pass.
- Activate/close the hot-seat modal through its real button. On the build that
  closes it, assert the open modal hierarchy is empty and NavEnableKeyboard is
  already off, before any extra settle frame. Queue Tab after releasing the
  activation key, build the next normal frame, and require no HUD navigation
  movement. A captured boundary event is permitted as described above; after that
  normal frame, a fresh Tab must be delivered to the player path.
- After one ordinary owner-free frame, require capturesKeyboard=false and a fresh
  U/R event delivered. Repeat with a text field active to ensure the cleanup does
  not forcibly clear genuine ownership. Retain the settled modal and menu tests.

The implementation review also found a test-harness focus trap unrelated to the
production capture change: clicking UNDO, then directly recreating ply 1, causes
`##recent` to reappear and take navigation focus. Tab in that text-only window does
not prove HUD button navigation. Use the actual view-mode HUD button (approximately
220,658 at 1280×720), whose activation preserves history, as the pointer-focused
control for the nav test; alternatively assert the intended controls window is the
actual focus owner before sending Tab. Do not change production navigation to make
an incorrectly focused test pass.


## Implementation status

Implemented the public navigation capture setting, the shared shell-derived navigation
policy at build entry and exit, and the single keyboard ownership query combining IO
capture with the current modal popup hierarchy. SDL backend delivery and main's key
mapping/capture gate remain unchanged.

The real SDL boundary regression failed before implementation; the additional first-
modal-frame and modal-close policy checks failed before the timing correction. The
complete case now passes 500 assertions across both themes: idle pointer/keyboard
focus, held widgets, Tab/Enter Undo activation, F12 text input, hot-seat ownership,
pause navigation, confirmation/promotion choices and trailer keys. It checks event
capture agrees with the public ownership getter. All 330 render/app cases pass
(4,915,208 assertions) on llvmpipe Mesa 26.2.3 with Vulkan validation enabled.

Live Xvfb captures in `out/m23/keyboard/` verify pointer e2→e4 followed by real U,
U after Tab, pointer Undo, R reset, F flat/solid view, F12 typing `urfg[]` without
moving the game and U after closing the console, plus visually verified Escape
pause/resume in both themes. Manifold also covers the pause save-name text field
and torus G/bracket shape/inversion shortcuts. Live hot-seat captures show white
partial entry cancelled by Tab, black partial entry cancelled by backslash, U entering
a player coordinate without Undo, and Tab/Enter resuming from pause. Trailer captures
verify Space pause/resume, Shift+Right edit stepping, Enter recording, Delete removal
and Escape exit. A real promotion popup blocks U/R and accepts a keyboard choice.
All 43 GUI gates pass (56.96 seconds). The full precommit gate passes, including
the property sweep (423.10 seconds).
