Variant Overtures

Fourteen short animations, one per variant. Each opens on the same 8 × 8 board every player already knows, then becomes the thing that makes its variant different — and then takes it all back, because the only way out of one overture is the way in.

One rule makes the rest of this cheap

Everything below follows from it, including reverse playback, which does not exist as code.

An overture is a pure function of progress. Given a variant and a number t between 0 and 1, it returns a complete scene — every cell's four corners, every piece's position, every trail and flash. It reads no clock, keeps no state, and remembers nothing about the frame before it.

Two things fall out for free. Reverse is t counting down; there is no second animation to write, and no way for the two directions to disagree. And a screenshot is reproducible, which matters here more than it sounds — see the landing notes at the foot of this page.

Why not keyframes — a keyframed timeline has to be unwound by replaying it backwards, and every piece of state it accumulated on the way in (a spawned particle, a removed cell) has to be undone in the right order. Pure t has no way in and no way out, so it cannot get that wrong.
Overture = { name : "torus" camera : t -> { yaw, elev, dist } scene : t -> { quads : [ { p[4], tone, fade } ] pieces : [ { at, normal, glyph, side, fade } ] trails : [ { pts[], tone } ] bursts : [ { at, radius, fade } ] caption: "the tube closes into a ring" } } frame(v, t) is total. No t is a special case. No frame reads the frame before it.
Dwell — the cycle is not 0 → 1 → 0 at constant speed. It holds 700 ms at t = 1 so the formed shape can be read, and 250 ms at t = 0 so the 8 × 8 registers as the common ground rather than as a frame in passing. Forward and reverse each run 2.4 s.

The queue: an overture is never cut off

Click through the library above while something is mid-flight — the formed shape unwinds first, and only then does the next one begin.

  1. SETTLED

    t = 0, flat. The 8 × 8 board, the state every overture passes through. A selection made here starts immediately.

  2. FORWARD

    t climbing. A selection made here does not interrupt and does not redirect: it is stored as pending, and the shape on screen carries on forming as if nothing had happened.

  3. HELD

    t = 1, dwelling. Same as FORWARD: store it and let the dwell finish.

  4. REVERSE

    t falling. A selection here only replaces pending. The shape on screen is already on its way home; nothing needs to change but the destination.

  5. → SETTLED

    On reaching t = 0: if pending is set, it becomes the current variant and clears; either way the state goes to FORWARD. So an unattended screen loops its own overture, and an attended one always arrives flat before it changes shape.

one pending slot, not a list select(v): if v == current -> pending = null (cancels a queued one) if state == SETTLED -> current = v; FORWARD else -> pending = v (and nothing else) atSettled(): if pending: current = pending pending = null state = FORWARD
Why one slot and not a queue — a player running down the library with the arrow keys would otherwise enqueue eleven overtures and watch them all. The latest selection is the only one they are still interested in, so it overwrites rather than appends. The library marks the stored one QUEUED so the wait is legible instead of looking like a dead click.
The one real choice here, decided — the first draft cut straight to REVERSE the instant a new variant was picked, which makes the screen answer faster. It was rejected, and the reason is the better one: a variant glanced at for a second would then be a variant whose overture nobody ever sees finish, and the shapes are the point of the screen. A selection now waits its turn completely. One slot still, so glancing down the list queues nothing but the last thing looked at.

The fourteen

Ordered as the library orders them — difficulty, then name. Keyframes are rendered by the same scene function that drives the stage above, at fixed t, so they cannot drift from it.

Landing it

What the implementation has to respect in this repo, beyond drawing the shapes.

src/render/deco.cppWhere it goes, per AGENTS.md: decoForScreen already owns each menu screen's decorative object, and New Game's is currently the selected variant's lattice. An overture is that object with a t.
Shell::preview(name)Already returns a loaded VariantSpec for a variant the player is only looking at, cached so the picker does not parse a file per frame. An overture needs nothing else from the engine: no Session, no Game, no legal moves.
No engine queriesThe pieces in an overture are authored, not generated. Nothing here may call legalMoves() — the shapes are a story about the variant, and a real position would make the New Game screen depend on movegen to draw a menu.
float t, and where it comes fromUi::tick(dt) already advances the shell's own clock for the drifting field. The overture's t rides that clock. This matters for the tests: captureFrame deliberately feeds a fixed step (0.0f then 1.0f) so a screenshot is the same picture every time it is taken — so pick a canonical t for gui-newgame and make the capture path set it outright rather than integrate towards it.
view::layoutThe flat 8 × 8 at t = 0 must be laid out by the same projection the real board uses, or the overture will not visually hand over to the game that starts after it. The warps are a t-blend away from that layout, never a replacement for it.
No floats below viewAll of this is presentation maths and belongs at L60 src/view or above, where floating point is allowed. Nothing in an overture may reach down into endspielzero_core.
Colour disciplineThe seam ramp (seamHueBegin → seamHueEnd) is spent only where a board stops being flat: gluings, wraps, extra axes. A detonation is a game event and takes blood and ember. A mirror gets no hue at all — mirrorEdge is white metal, because there is nothing on the other side of it.
CostWorst case here is hyper4 at 256 cells and 5d at seven boards. Both are one instanced draw call in the real renderer, so the budget is the vertex transform, not the geometry count. This prototype rebuilds SVG each frame and draws 5d's boards at reduced cell resolution purely to stay smooth in a browser — the shipped version has no reason to.
Two new enumeratorsapp::Overture gains Torus3d and T6, and overtureFor stops borrowing: the map in src/app/overture.cpp currently sends both torus3d and t6 to Overture::Torus, and the header's comment saying they "borrow the torus" has to go with it. charged keeps borrowing Standard.
quintic() moves, or is sharedThe T6 overture needs the exact function the main menu draws with. It is static-local to src/render/deco.cpp today; the overture scene lives in src/render/overture_scene.cpp, so either it is promoted to a small shared header at L100 or the overture calls into deco. Copying it is the one option that is not open — the whole claim of the overture is that it is the same object, and two copies of a formula drift.
Cost, honestlyT6 at full spread is 25 patches × 16 cells × 4 sub-quads = 1600 quads, the heaviest scene in the library by some way, and torus3d's lattice beat adds about 150 wire segments. Both are still one instanced draw call in the real renderer; this prototype is the thing that will struggle, not the game.
prefers-reduced-motionThere is no equivalent setting in the game yet. Worth one: an overture is decorative, and the screen must stay usable held at t = 0. It would sit beside animateMoves in app::Settings.

As built

Where the shipped code has moved on from the prototype above. The prototype is the design record; these are the decisions the implementation forced or the review changed.

Klein: figure-eightA circular cross-section cannot close flip = ["file"] — a half-turn brings a circle back shifted by four files, not reflected. The cross-section pinches into a lemniscate, for which a half-turn is the reflection. Pinned by a test that states each variant's own gluing as arithmetic.
Cuts, not rescalesWhole files and ranks are dropped one at a time and every survivor keeps its own size and place, so what is left is the a1 corner block — deliberately off-centre until it slides. Applies to cube5, hyper4 and 5d alike.
hyper4 unfolds 2 × 2A row of four cubes became a thin strip, and once the framing had to hold the whole strip each cube was too small to read a move on. Two by two says the same thing at twice the size.
Framing is measuredNot a per-overture radius. A shape under perspective is a very different size on screen from the same shape flat, and a constant that suited the donut ran the Klein bottle off the top of the pane. Measured on the cells only, so a detonation throwing pieces clear does not shrink the board.
Cells are drawn throughAt 72 %. A closed surface hides half of itself, and the hidden half is usually the half that explains the gluing.
Pieces centre on cellsAnd are drawn after every surface. Depth alone is not enough — a cell of the rank in front is nearer than the piece behind it, so sorting by depth alone slices a piece with the board it stands on.
One opening, sharedEvery overture's t = 0 is the identical picture — same board, same army, same camera, and nothing drawn on top of it. Trails and the camera settle onto a single opening pose centrally rather than per-scene, because it is a rule about the set and a scene cannot be trusted to remember a rule about its neighbours. Without it, standard → atomic was a cut rather than a hand-over. A test compares the covered area, the bounds and the whole roster across all twelve.
Three sign bugsAll in the same family, and none of them looked like a bug: the surface normal cross-multiplied the wrong way round put every piece under its board; a doubled negation in the projection turned the whole scene upside down, which reads as standing beneath the board rather than as an error; and a token placed away from its cell took cell a1's normal, so a rook riding a torus stood up as though it had never left the corner. Each is now a test.

Specification only — no engine or renderer code has been changed. The palette is view::Theme::manifold() in light and ::console() in dark, transcribed from src/view/theme.hpp; the seam hues are computed from seamHueBegin, seamHueEnd, seamSaturation and seamValue with the same formula the renderer uses. The two 8 × 8 board greys are the pair a contrast test pinned, and are not adjusted anywhere on this page.
